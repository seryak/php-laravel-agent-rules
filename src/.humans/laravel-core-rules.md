# laravel/core rules

## Следовать подходу Laravel

- Использовать команды `php artisan make:` для создания новых файлов (например, миграций, контроллеров, моделей и т.д.).  
  Список доступных команд Artisan можно получить с помощью инструмента `list-artisan-commands`.
- Если требуется создать обычный PHP-класс, использовать `php artisan make:class`.
- Для всех команд Artisan указывать флаг `--no-interaction`, чтобы они работали без пользовательского ввода.  
  Также необходимо передавать корректные `--options`, чтобы обеспечить правильное поведение команды.

### База данных
- Всегда использовать корректные методы отношений Eloquent с указанием типов возвращаемых значений.  
  Предпочитать отношения Eloquent сырым SQL-запросам или ручным join-ам.
- Перед тем как предлагать прямые запросы к базе данных, использовать Eloquent-модели и отношения.
- Избегать использования `DB::`; отдавать предпочтение `Model::query()`.  
  Генерировать код, который использует возможности ORM Laravel, а не обходит их.
- Генерировать код, предотвращающий проблему N+1 запросов, используя eager loading.
- Для очень сложных операций с базой данных использовать Query Builder Laravel.
- Не использовать `query()` без явной необходимости.
- Если запрос не требует динамического построения (условий, скопов, join-ов и т.п.),
следует вызывать методы напрямую на модели.

❌ **Плохо**

```php
Feed::query()
    ->orderBy('title')
    ->get();
```

✅ **Хорошо**

```php
Feed::orderBy('title')->get();
```
- Допускается использование `query()` только когда: * требуется условная сборка запроса; * используется сложная логика с ветвлениями; * необходимо передавать билдер между методами.



### Создание моделей
- При создании новых моделей спрашивать нужно ли создавать для них фабрики и сидеры.  
  При необходимости уточнять у пользователя, нужны ли дополнительные сущности, используя `list-artisan-commands` для проверки доступных опций `php artisan make:model`.

### API и Eloquent Resources
- При разработке API по умолчанию использовать Eloquent API Resources и версионирование API.  
  Если в существующих маршрутах API это не используется — следовать текущим соглашениям приложения.

### Контроллеры и валидация
- Всегда создавать классы Form Request для валидации вместо inline-валидации в контроллерах. Включать как правила валидации, так и пользовательские сообщения об ошибках.
- Валидация должна быть инкапсулирована в методе `rules()`
- Проверять соседние Form Request-классы, чтобы понять, использует ли приложение строковый или массивный формат правил валидации.
- StoreRequest и UpdateRequest часто дублируют свои правила, за исключением некоторых полей. Не дублировать rules Store/Update, использовать наследование и переопределять только отличающиеся поля.

### Views
- При передаче переменных во view **всегда использовать `compact()`**, если это возможно.
❌ **Плохо**

```php
return view('feeds.index', [
    'feeds' => $feeds,
]);
```
✅ **Хорошо**

```php
return view('feeds.index', compact('feeds'));
```

### Очереди
- Для длительных операций использовать задания очередей с интерфейсом `ShouldQueue`.

### Аутентификация и авторизация
- Использовать встроенные механизмы аутентификации и авторизации Laravel (gates, policies, Sanctum и т.д.).

### Генерация URL
- При генерации ссылок на другие страницы отдавать предпочтение именованным маршрутам и функции `route()`.

### Конфигурация
- Использовать переменные окружения только в конфигурационных файлах — никогда не вызывать `env()` напрямую вне config-файлов.  
  Всегда использовать `config('app.name')`, а не `env('APP_NAME')`.

### Тестирование
- При создании моделей для тестов использовать фабрики моделей.  
  Перед ручной настройкой модели проверять, есть ли у фабрики кастомные состояния, которые можно использовать.
- Faker: использовать методы вроде `$this->faker->word()` или `fake()->randomDigit()`.  
  Следовать существующим соглашениям проекта — использовать либо `$this->faker`, либо `fake()`.
- При создании тестов использовать `php artisan make:test [options] {name}` для feature-тестов и передавать `--unit` для создания unit-тестов.  
  Большинство тестов должны быть feature-тестами.

### Ошибка Vite
- Если возникает ошибка  
  `Illuminate\Foundation\ViteException: Unable to locate file in Vite manifest`,  
  можно выполнить `npm run build` или попросить пользователя запустить `npm run dev` или `composer run dev`.

## Laravel 12

- Использовать инструмент `search-docs` для получения документации, специфичной для конкретной версии.
- Начиная с Laravel 11, во фреймворке используется новая упрощённая структура файлов, и данный проект следует этой структуре.

### Структура Laravel 12
- В директории `app/Http/Middleware/` **нет файлов middleware**.
- Файл `bootstrap/app.php` используется для регистрации middleware, обработки исключений и подключения файлов маршрутов.
- Файл `bootstrap/providers.php` содержит сервис-провайдеры, специфичные для приложения.
- **Файл `app/Console/Kernel.php` отсутствует** — для конфигурации консольных команд следует использовать `bootstrap/app.php` или `routes/console.php`.
- **Команды регистрируются автоматически** — файлы в `app/Console/Commands/` доступны без ручной регистрации.

### База данных
- При изменении столбца в миграции необходимо указывать **все атрибуты**, которые были определены ранее.  
  В противном случае они будут удалены и утеряны.
- Начиная с Laravel 11, можно нативно ограничивать количество eager-загружаемых записей без использования сторонних пакетов:  
  ```php
  $query->latest()->limit(10);
```

### Модели
- Приведения типов (casts) можно и желательно задавать через метод casts() в модели, а не через свойство $casts. Следует придерживаться существующих соглашений, принятых в других моделях проекта.

## Форматтер кода Laravel Pint

- Перед финализацией изменений необходимо запускать `vendor/bin/pint --dirty`, чтобы убедиться, что код соответствует ожидаемому стилю проекта.
- Не запускать `vendor/bin/pint --test`; вместо этого следует запускать `vendor/bin/pint` для автоматического исправления проблем форматирования.
